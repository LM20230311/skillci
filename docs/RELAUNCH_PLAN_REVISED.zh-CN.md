# SkillCI 收敛后的再启动执行方案

> 修订日期：2026-11-04
>
> 当前正式版本：`v0.5.0`（2026-11-05 发布）
>
> 状态：本次收敛修订已完成；以下功能、版本与外部采用目标均为待执行计划。
> 来源：[原始再定位提案](RELAUNCH_PLAN.zh-CN.md)。后续迭代范围以本方案为准，实际进度统一记录在 [PROJECT_PLAN.md](PROJECT_PLAN.md)。

## 1. 本次决定

继续使用 SkillCI 的仓库、npm 包和品牌，围绕一个具体任务迭代：

> **让维护 Agent Skill 仓库的人，在 PR 中看见风险与权限变化，并用 CI 阻止不符合仓库策略的更新。**

当前产品定位：

- 中文：**Agent Skills 的权限与行为回归 CI：发现指令文件、审查权限变化、检查受限环境中的行为。**
- English: **Policy and regression CI for Agent Skills: discover instruction files, review permission changes, and check behavior in a constrained workspace.**

“Skill 供应链 CI”保留为长期方向。只有逐步具备来源与完整性验证、版本锁定、发布物关联等能力后，再评估是否将其作为首页主定位。SkillCI 自身 npm 包使用 Trusted Publishing，并不意味着它已经能验证用户安装的第三方 Skill 供应链。

保留静态审计、策略、回归案例、Docker 行为 runner、GitHub Action 和 npm 分发。下一次发布从 `skillci discover` 开始。

## 2. 原方案如何收敛

| 主题 | 修订后的决定 | 原因 |
| --- | --- | --- |
| 品牌与仓库 | 保留 SkillCI | 已有可用引擎、稳定命令与双渠道发布流程 |
| 首批用户 | Skill 仓库作者与维护者 | 能直接修改 CI、确认误报并持续使用 |
| 长期用户 | 安装者、工程/安全团队、目录维护者 | 先积累可核验采用，再验证这些用户的独立流程 |
| 核心定位 | 权限与行为回归 CI | 与现有可交付能力一致 |
| 行为能力 | 使用 behavior evidence / regression 表述 | Node API 观测与 fixture 测试不构成任意 Agent 行为证明 |
| 第一个版本 | 自动发现、稳定 discovery JSON、审计接入 | 先解决用户不知道扫描哪里的接入障碍 |
| 第二个版本 | SARIF 与 GitHub 集成 | 让 finding 进入现有审查界面 |
| 基准与传播 | 先 10–20 个固定版本样本，再找 3–5 个维护者协作 | 先确认发现是否有用、误报能否处理 |
| DSH | 条件触发的后续 adapter | 有真实维护者或目录需求再投入 |
| Badge | 后置到可验证报告之后 | 展示检查结果、版本与时间，避免被理解为安全认证 |
| 遥测 | 首轮使用公开、可核验信号 | 当前无需为指标增加收集服务 |
| 商业化 | 先访谈和试用验证 | 团队付费仍是假设 |

## 3. 已知事实、推断与待验证假设

以下是 2026-11-04 审阅时的快照，不作为持续实时统计。

| 证据 | 已核验内容 | 可支持的判断与限制 |
| --- | --- | --- |
| [SkillCI](https://github.com/LM20230311/skillci) 与 [npm 下载 API](https://api.npmjs.org/downloads/point/2026-10-05:2026-11-03/skillci) | 约 1 star；上述区间下载 19 次；正式版本 `v0.4.1` | 公开采用信号弱；下载不等于独立用户，低采用也不能单独证明是定位问题 |
| [dsh-plugin-health](https://github.com/EasonMWS/dsh-plugin-health) 与 [npm 包](https://www.npmjs.com/package/dsh-plugin-health) | 项目存在且活跃；核验时 npm 版本 `2.2.1` | 同名与安装健康方向已有产品，无需另开同名项目 |
| [dsh-plugin-radar](https://github.com/AdamPlatin123/dsh-plugin-radar) | 约 1,493 stars；项目自述持续发现和运行验证 | 表明已有维护投入；项目自报的候选数、测试次数不等于去重可用插件数 |
| [dsh-suite](https://github.com/whyihaveyou/dsh-suite) | 约 64 stars；提供目录与兼容测试 | 相邻能力存在；不能仅凭 star 数判断竞争强度或用户需求规模 |
| [awesome-dsh-plugin#2582](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/issues/2582) | 报告特定 DSH 版本下部分高星插件安装/启动失败 | 支持兼容性需求存在，不能直接证明用户需要 SkillCI 的权限门禁 |
| [dsh-market#1008](https://github.com/dsh-market/dsh-market/issues/1008) | 请求安装体积、兼容矩阵与权限范围信息 | 支持用户需要安装前信息，但尚不能证明会采用本项目 |
| [GitHub SARIF 上传文档](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file) | GitHub 可消费第三方 SARIF | SARIF 是可行接入方式；仍需实际上传验证和正确权限 |

据此保留的推断：现有发布基础值得继续复用；降低接入成本、验证 finding 价值，比扩张通用规则数量更值得优先尝试。

以下仍是假设：

- 维护者愿意为 Skill 更新配置持续 CI，而非只做一次扫描。
- 现有规则在真实样本上有足够的精确性和可操作性。
- DSH adapter 能带来目标维护者，而不只是短期曝光。
- 团队愿意为共享策略、例外审批或审计记录付费。

原文“尚无跨 Agent 标准”“赛道已是红海”等表述不作为立项事实。需要系统竞品样本与维护者反馈才能确认。后续市场数字必须包含日期、来源和候选/去重/已验证口径。

## 4. 现有能力与对外表述

静态审计识别文本中的风险信号；策略检查判断输入是否违反声明的限制；`policy diff` 比较两份策略的权限变化。当前并未实现“从任意 Skill 更新自动推导完整权限变化”，不能将这件事写成现有功能。

行为 runner 运行的是明确声明的 fixture 命令。它不会自动启动真实 Agent，也不能由一个 fixture 的通过结果推导所有模型、输入和版本都会遵守相同边界。

`v0.4.1` 通过 Docker 禁网、复制工作区等限制执行，并观测部分 Node 文件、子进程和网络 API。任意二进制、Shell 内部操作、原生模块、绕过或篡改 Node 预加载器等情况，不属于完整观测承诺。行为断言通常在执行后判断失败；报告失败不等于所有违规操作都被执行前阻止。

因此：

- “发现到 Skill”只说明文件符合目录或命名约定。
- “关联了 policy”只说明找到了配置及其验证结果。
- “通过审计”只说明当前输入通过了对应版本的检查。
- “通过行为案例”只说明该 fixture、命令与输入的本次执行满足断言。

报告应明确工具版本、输入版本、检查类型和观测范围；无法确认的覆盖状态显示 `unknown`，不显示为安全。未来若宣称强制权限边界，需要独立实现、验证相应机制。

## 5. 交付顺序与版本边界

版本号为拟定里程碑；发布前按实际兼容性决定。每个版本达到验收后再进入下一步，按反馈允许收缩范围。

### v0.5.0：找到该检查的文件

用户结果：在已有仓库运行一条命令，得到可审阅、可直接用于现有 `audit` 的文件或目录路径，无需移动 Skills。

范围：

- `skillci discover [path] [--format markdown|json]`，沿用现有 CLI 的格式选项习惯。
- 优先支持 Codex、Claude Code，再补 Cursor / Copilot 的项目级目录约定；至少 3 个宿主经测试可发现才完成本里程碑。
- 区分 `skill`、`instruction` 等发现类型；标记识别依据，不将所有指令文件都视为可安装 Skill。
- 为共享目录允许多个宿主标记，输出去重且稳定排序。
- discovery JSON 包含 `schemaVersion`、工具版本、相对路径、发现类型、宿主及识别依据、诊断信息。
- 明确默认扫描根目录、忽略目录和符号链接规则；默认不跟随逃出根目录的链接，不读取家目录；全局 Skills 延后。
- 报告读取失败、无效根目录和未支持输入；空结果有明确提示，不能被理解为“没有风险”。
- 提供从 discovery 结果运行现有 `audit` 的示例，保证用户能走到第一份风险报告。
- 双语 README 同步更新定位、真实命令、支持矩阵和边界。

策略覆盖在这一版只展示能证实的内容：明确传入或按文档约定关联的 policy、解析验证结果。禁止通过“附近存在 policy.yml”直接推断文件被正确保护。无法可靠建立关联时，先不提供覆盖百分比。

验收：

- [x] 对照实现时的各宿主官方约定记录来源与核对日期，见 [发现契约](DISCOVERY.zh-CN.md)。
- [x] 至少 3 个宿主有正常、空目录、混合宿主、嵌套、重复路径、链接越界和权限错误测试。
- [x] Markdown 与 JSON 对同一输入表达一致，JSON 有版本化样例。
- [x] discover 不写用户文件、不执行 Skill、不联网获取依赖。
- [x] 在 3 个固定 commit 的公开仓库上复核发现清单；范围与结果见 [验证记录](DISCOVERY_VALIDATION.md)。
- [ ] 一名未参与实现的人按 README 在 5 分钟内完成发现与静态审计，记录卡点。
- [ ] 原有 CLI、Action、构建和发布验证通过；版本引用双语一致。

不纳入此版：SARIF、badge、DSH、公开排行榜、全局目录扫描、自动修复和遥测。此版稳定的是 discovery schema；现有 audit JSON 如需演进，应另行明确兼容性方案。

### v0.6.0：让报告进入 GitHub 审查流程

用户结果：维护者能在 GitHub 中定位风险，并将检查作为 PR 门禁。

范围：

- 增加 `audit --format sarif`，生成合法 SARIF 2.1.0。
- 规则元数据提供稳定 ID、风险说明、修复建议；保留现有规则 ID。
- 相对 URI、行号、可复用的 fingerprint；正确表达 suppression。
- 完善 Action 的路径输入和多结果处理，保持已有显式路径用法兼容。
- 给出报告写入、上传、门禁退出状态的完整工作流；即使发现高风险而退出失败，也能上传报告。
- 保留 Markdown/JSON artifact 作为无法启用 Code Scanning 时的可用交付。

验收：

- [x] schema 校验通过，本项目公共仓库真实上传后，GitHub 告警关联正确源文件位置；见 [线上验证记录](SARIF_VALIDATION.md)。
- [x] 受控 fixture 同一 finding 重跑/移行不产生重复；修复后匹配分支/category 实例自动关闭，见线上记录。此结论不扩展到任意编辑。
- [x] primaryLocationLineHash 修复通过固定上游向量及新分支三阶段线上验收，全部上传日志无指纹不一致警告；fork PR 与发布仍单独验收。
- [ ] secret、绝对宿主路径、Markdown/URI 特殊字符有专门处理与回归样例。
- [ ] 默认只输出必要证据；脱敏规则不以“隐藏所有上下文”替代可解释性。
- [ ] 文档注明 `security-events: write`，并验证公共仓库、fork PR 权限受限和私有仓库适用范围。
- [ ] 记录 GitHub Code Scanning 的使用条件：公共仓库可用；私有/内部仓库需核对组织套餐与 Code Security 配置。

此版不建设独立结果平台，也不强制用户启用 GitHub 付费功能。报告脱敏检查应覆盖新输出和现有相关输出，发现缺陷按实际风险优先处理。

### v0.7.0：用真实样本验证价值

用户结果：能参考有复现步骤和人工复核记录的报告，并找到真实 CI 接入案例。

范围：

- 建立 10–20 个公开仓库样本的 manifest，固定 commit、工具版本、规则配置、来源与许可证信息。
- 首轮只做静态扫描和人工复核；行为执行仅用于另行评审的 fixture。
- 样本包括正常教学片段、合理的高权限 Skill、已知危险案例，避免只挑会触发规则的输入。
- 发布聚合结果、错误分类和复现命令；不以“高风险命中”直接指控项目恶意。
- 联系约 5 位维护者，争取 3–5 个自愿协作的试用；提交外部 issue/PR 前另行取得授权。
- 获得可验证报告后，再决定是否增加静态 SVG badge。badge 表达版本、日期和检查结果，链接到报告。

验收：

- [ ] 每条公开结论可追溯到固定输入及复核记录。
- [ ] 公开报告不包含秘密、个人目录、未获许可的完整文件复制。
- [ ] 至少获得 3 位维护者的可操作反馈，记录接受、误报、不清楚及拒绝原因。
- [ ] 目标为 3 个独立维护的外部仓库启用 CI；若未达到，记录反馈并判断原因，不伪造采用。
- [ ] 公开报告与功能交付完成度、外部采用结果分开记录。

## 6. DSH、badge 与商业功能的进入条件

DSH adapter 的启动条件：至少一位实际维护者或一个目录愿意评审输出，且有 3 个固定版本样本可用于验证。范围限于只读识别 bundle、patch、Skill 与生命周期脚本的相关信息。字段与文件名以实施时官方格式和样本核验为准，不把原文列出的 `dsh.bundle`、`cordis.patch.yml` 当成未经验证的稳定规范。

DSH 安装健康项目可成为结果消费者或协作对象。兼容失败证据不直接证明安全扫描需求，adapter 采用与通用 SkillCI 采用分别记录。

Badge 必须标识检查对象版本、时间和工具版本，并能跳转到结果；不使用 “safe”“certified” 等标签。动态 badge 服务与排行榜等待持续消费者需求。

团队功能先访谈：共享 policy、例外审批、报告保留中，哪一项已造成实际成本。至少 2 个团队愿意试用同一个具体流程后，才设计最小团队功能。SSO、SCIM、私有 registry、SLA 与云控制台保留为远期假设。

## 7. 节奏与工作量

以开发工作日估计，不作为固定日历承诺。外部采用取决于维护者反馈，单列观察窗口。

| 阶段 | 估计投入 | 退出条件 |
| --- | --- | --- |
| v0.5.0 | 5–8 个开发工作日 | 发现、审计路径与支持矩阵验收通过 |
| v0.6.0 | 4–7 个开发工作日 | SARIF 实际上传、门禁与脱敏验证通过 |
| 第一轮样本和试用 | 5–10 个工作日，可与反馈等待交错 | 完成固定样本复核，得到维护者反馈 |
| 方向复盘 | 第一次有效接触维护者后 4–6 周 | 判断保留、收缩或调整用户场景 |

首周只围绕 v0.5.0：先完成宿主约定与发现模型，再实现适配器、验证真实仓库，最后修订双语接入流程。SARIF 在 discovery 稳定后单独推进。

若发现现有规则在首批样本上误报严重，先暂停扩大扫描范围，优先修复最影响使用的规则并发布小版本。代码完成不等于有人愿意采用。

## 8. 指标、复核口径与转向规则

第一轮不用新增遥测。采用来源为公开工作流配置、成功的 run、维护者反馈和自愿提供的证据；不扫描或推测私有使用情况。

| 指标 | 口径 | 第一轮目标 |
| --- | --- | --- |
| 可核验试用 | 不同外部维护者提供固定输入的结果或公开 run；本项目批量代跑不计入 | 5 个仓库 |
| 持续 CI 采用 | 独立外部仓库默认分支保留工作流，且至少有一次成功 run | 争取 3 个仓库 |
| 重复使用 | 同一外部仓库在不同 commit/PR 上至少运行两次 | 争取 2 个仓库 |
| 有用 finding | 维护者确认需修复或需要明确策略例外，保留链接 | 争取 3 条 |
| 误报 | 人工确认不符合规则定义的 finding 数 / 已完成判定的 finding 数 | 逐规则报告数量与比例，不以小样本概括全生态 |
| 待判定 | 上下文不足或维护者未回复的 finding | 单列，不当成真阳性或误报 |
| npm 下载 | 固定日期区间的包下载次数 | 仅看趋势，不能换算用户或收入 |

规则“命中真实的高权限行为，但用户愿意允许”与“规则错误识别”分开记录。发现器另记应发现、实际发现、漏识别与误识别数量。首轮报告样本构成和分母，不给无依据的检测覆盖率。

当有至少 5 次完整试用和 3 次维护者交流后，才作第一轮方向判断：

- 已有重复使用且维护者确认 finding 有用：继续完善 CI 接入。
- 接入卡住、但维护者认可报告：收缩到接入与误报修复。
- 维护者只需要安装前的一次扫描：重新评估一次性审计场景，不强求 CI。
- 充分试用后仍无可操作 finding 或重复使用意愿：暂停新宿主、新规则和商业功能，调整目标任务。

若没有接触到足够维护者，结论是“分发验证不足”，不能直接判定没有需求。30/90 天的星标、下载或团队数不作为硬性承诺；每次复盘记录实际证据和下一项假设。

## 9. 每次迭代与发布要求

1. 在 PROJECT_PLAN 选择一个里程碑，列出本次范围、验收和明确延后项。
2. 实现并验证关键行为，保持现有命令和规则 ID 的兼容性。
3. 同步 README 各语言版本、CHANGELOG 与计划；未实现命令不得写成可用能力。
4. 发布前运行仓库规定检查，完成具体提交、目标分支、tag 和版本的核对。
5. 遵守当前用户的 Git 操作确认规则：推送或集成前列出来源 ref、目标 ref、remote、是否改写历史、精确操作及风险，等待明确确认。
6. 发布经授权的 GitHub tag/Release，由 OIDC workflow 自动发布同版本 npm；独立验证两端后记录结果。
